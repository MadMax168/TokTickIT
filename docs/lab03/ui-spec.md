# Sprint 3 UI contract

Status: Draft. Requirement/endpoint/test IDs are defined in the companion [specification](specification.md), [API contract](api-spec.md), and [test plan](tests.md). This is a continuation of [Lab 2 Zen Green](../lab02/ui-spec.md), not a new visual system.

## Shared presentation and feedback

Reuse the Lab 2 shell, field groups, read-only fields, buttons, badge/state styles, file controls and table/card conventions. Tokens: primary `#006B3C`, secondary `#0B7A46`, pale `#EAF6EF`, page `#F5F7F6`, surface `#FFFFFF`; existing dark text, read-only surface, error, warning and success semantic tokens remain. Use Inter/system sans-serif, body at least 1rem and line height about 1.5, 4px spacing scale, and practical 44px touch targets. No new palette or visual system; bring new screens into the existing Lab 2 component styling, even where global CSS defaults differ.

Every screen below uses these states when applicable. The per-screen table explicitly identifies empty/no-results and modes; read-only screens have no saving or create/edit mode unless an action panel is specified.

| State | Required behavior |
| --- | --- |
| Loading | Announce progress with role=status, retain structural headings, hide stale resource content and disable dependent actions. Never show protected content before current-user completes. |
| Saving | Busy action label and disabled duplicate submit; preserve entered data, except passwords are cleared on successful submission or session loss. |
| Success | Announce the saved outcome; render server-returned values rather than optimistic status. Reset a comment/note composer only after confirmed 201. |
| Validation | Required text indicators, associated field errors, focus first invalid field and a safe summary. Client validation mirrors the API but never replaces it. |
| Empty | Explain why a valid collection has no items; offer a permitted creation/recovery action. No blank panel. |
| No-results | Distinguish filtered no-match results from an unfiltered empty list; show Clear filters. Out-of-range page offers Return to first page. |
| Forbidden | 403 FORBIDDEN shows Access unavailable and a role-permitted navigation action; do not render cached restricted content. A 403 PASSWORD_CHANGE_REQUIRED redirects to Change Password and clears protected caches. |
| Safe failure | Generic error with appropriate retry. 401 clears identity/data and shows Login with Session ended. Resource 404 is Ticket not found/User not found without existence hints. 409 explains conflict and refreshes current state before a new deliberate submission. No raw error dumps. |

Dialogs have labeled titles, focus trapping, Escape/cancel, initial focus on a safe control and return focus to the trigger. Cancel sends no mutation. Announce success/loading politely and errors as alerts; do not repeatedly announce while typing. Logout failure is displayed with retry; it must not claim the server session was revoked. Clear locally displayed protected data during logout. Ignore in-flight results from the ended identity.

## Requester collaboration and attachments (UI-06)

Public Comments have a heading, author/time and plain-text body, oldest first; wrap long text safely. Composer has a 2000-character limit/counter and Post public comment. No automatic resubmission after uncertain network outcome: reload the list and ask the user to inspect before retrying. The indicator reads “Problem Appears Resolved” with help text “This informs IT Staff; the formal ticket status does not change.” It remains usable in every status, and is not checked automatically when Staff resolve a ticket.

Preserve Lab 2 active/removed attachment metadata, filename/type/size/date, one-file uploads, five active files and 5 MB guidance. Only the owning Requester has Upload/Remove, in every status. Removal confirmation names the file and requires the reason before DELETE. Files failing upload do not erase the created ticket. Staff/Admin attachment panels expose read-only metadata and permitted active Download only.

## Queue layout and field justification (UI-07)

Desktop at >=992px uses a semantic table: Ticket Number + Summary (identify/open the issue), Requester (who needs help), Status (current stage), IT Priority (triage), Ticket Owner (responsibility/unassigned, with role label), Last Updated (recent ticket activity). Ticket Date, Category, Related System and Requested Priority appear in detail; these are omitted from queue columns to keep it readable. Queue sorting still includes ticketDate/updatedAt/ticketNumber/summary using a labeled single-field control. IT Priority initially displays the Requested Priority value and always has a Low, Medium or High label; an inactive owner is explicitly labeled Inactive. The total count is filtered, not a KPI dashboard.

Tablet 768–991px and mobile <768px use labeled cards with every queue table field and the same Open Ticket action. Filters and page controls wrap/stack; there is no wide horizontally scrolling table. Preserve a meaningful reading and keyboard order across representations. Administrator and Staff share this list; Administrators can edit IT Priority in detail, while assignment/status controls are Staff-only.

## Staff detail actions and internal channel (UI-08)

Separate read-only request information from operational controls. Label Requested Priority and IT Priority distinctly. Claim appears only for unassigned mutable tickets. Assign/Reassign opens a panel of active IT Staff and Administrators from EP-14, showing each name and role; show current owner and confirm selected target before saving. Assignment does not say it opens a ticket. Empty assignee list disables assignment and explains no eligible active Ticket Owners are available. An assigned Administrator is displayed normally; assignment does not enable Staff-only claim/reassignment/status controls for that Administrator.

Status chooser displays only permitted targets from specification BR-15, using human labels. Every change opens a confirmation dialog naming current and next status. For Resolved/Closed/Cancelled, require a 3–200-character reason; no reason input for other transitions. An active Staff or Administrator owner satisfies the owner prerequisite; missing/inactive/ineligible owners disable unavailable transitions with an explanation. On 409, refresh detail and require a fresh selection/confirmation; do not silently replay the old action. IT Priority has a separate Save priority action for both IT Staff and Administrators and no Requested Priority editor. On creation it displays the copied Requested Priority; subsequent saves change only IT Priority.

Public Comments and Internal Notes are separately titled panels/composers, not a single composer with a hidden visibility toggle. Public panel help: “Visible to the Requester and support team.” Internal panel uses existing pale/warning styles plus text “Internal — visible only to IT Staff and Administrators.” Distinction must not depend on color. Use “Post public comment” and “Add internal note” buttons, with separate drafts and feedback. Do not insert notes into public cache entries. Both channels allow posting on terminal tickets.

## Administrator panels (UI-09)

Create: required Name, Email, single Role select, Initial password, Confirm password, Active checkbox default checked. Explain mandatory password replacement. The operator supplies the initial password to the user outside this application; no email flow or generated password display is required. Clear password fields on close/success. Save returns to the refreshed list.

Edit: Name, Email, one Role, Active; no password field. Existing Requesters with tickets cannot change role; Staff or Administrators with nonterminal assigned tickets must have those tickets reassigned before changing to Requester. Switching between eligible owner roles remains subject to Administrator safety rules. Deactivation is allowed for another such user and retains historical ownership. Confirm deactivation with user name and session-ending effect. No Delete or bulk action. Server-side last-Admin and duplicate-email conflicts appear beside the action/field and retain safe unsaved values.

Set initial password: distinct dialog with New initial password, confirmation field, and confirmation explaining all target sessions end and next login requires a change. If targeting self, successful setting ends the Admin session and returns to Login. No session is silently restored by activation or password setting.

## Responsive and accessibility acceptance

All screens follow Lab 2 breakpoints: centered sensible-width content >=992px, practical two-column groups at 768–991px, stacked fields and full-width panels below 768px. Login/password forms remain compact and centered; shell navigation may collapse but role/name/logout stay discoverable. Detail request/work panels can use two columns on desktop and stack on smaller screens. User list becomes labeled cards on tablet/mobile; panels become full-width dialogs without hiding actions.

Test 1280×900, 820×900, 390×844, 320px width and 200% text enlargement: no page overflow, clipping, hidden permitted actions or overlap, including long filenames/emails/comments and validation text. Capture every screen's applicable shared states for later visual review. Forms have programmatic labels, required attributes, associated errors, password reveal accessible state, logical headings, visible focus, semantic table headers, keyboard page controls and dialog focus restoration. Color is always accompanied by text. Check body-text contrast of at least 4.5:1 and UI/focus indicators at least 3:1 as project acceptance targets. Do not claim accessibility conformance from snapshots alone; include keyboard and semantic assertions.
